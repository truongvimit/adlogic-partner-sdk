# Google Mobile Ads Android threading and preload notes

Research date: 2026-09-26. The project uses the legacy Android API (`com.google.android.gms:play-services-ads:25.3.0`; see `versions.gradle`). The official documentation below is for the same Legacy API family.

## What Google documents

- **Interstitial load calls:** Google's Android interstitial guide explicitly says: “Make all calls to the Google Mobile Ads SDK (Legacy) on the main thread.” Its sample initializes `MobileAds` on a background thread, then switches to the main thread before calling `loadAd()`. See [Load an interstitial ad](https://developers.google.com/admob/android/interstitial#load_an_ad) (the note is immediately above the `InterstitialAd.load` example) and the sample implementation near the end of the same page.
- **Native `AdLoader.Builder`:** Google's native-ad guide explicitly recommends constructing `AdLoader.Builder` on a background thread. The Kotlin and Java snippets both wrap the builder in `Dispatchers.IO`/`new Thread`. See [Build an AdLoader](https://developers.google.com/admob/android/native#build_an_adloader).
- **Native request call:** The same native guide documents `adLoader.loadAd(...)` and `loadAds(...)`, but does not grant a general background-thread exception for those calls. The interstitial guide's SDK-wide main-thread note and the official examples' main-thread `loadAd()` pattern are the conservative contract for the Legacy SDK: build/configure the loader off-main if desired, then dispatch the actual ad-load call and any view/UI binding to the Android main thread.
- **Banner load:** The banner guide is explicit that `AdManagerAdView.loadAd()` “must be called on the main thread.” See [Load an ad](https://developers.google.com/ad-manager/mobile-ads-sdk/android/banner#load_an_ad). This confirms that ad-format APIs can have main-thread contracts even though network work is asynchronous.
- **Initialization is different:** Google recommends calling `MobileAds.initialize()` on a background thread because initialization can perform disk/network work. See [Set up the SDK](https://developers.google.com/admob/android/quick-start#initialize_the_google_mobile_ads_sdk) and the [MobileAds reference](https://developers.google.com/admob/android/reference/com/google/android/gms/ads/MobileAds#initialize(android.content.Context,%20com.google.android.gms.ads.initialization.OnInitializationCompleteListener)). Do not infer from this that `loadAd()` may be called off-main.
- **SDK load optimization:** Starting with GMA 21.0.0, `OPTIMIZE_AD_LOADING` can move ad-load tasks that require extended processing to background threads; from GMA 24.0.0 the flag defaults to `true`. This is an SDK-internal optimization and does not change the app-facing thread contract. See [Optimize initialization and ad loading](https://developers.google.com/admob/android/optimize-initialization#optimize_ad_loading).
- **Native preloading:** Google explicitly recommends using ad-load calls to build a cache before an ad is needed, so the ad can be shown with zero latency; cached native ads should be cleared/reloaded after one hour and destroyed when no longer used. See [Request ads / preload cache](https://developers.google.com/admob/android/native#request_ads) and [Release resources](https://developers.google.com/admob/android/native#release_resources).
- **Showing/registering native UI:** Google’s custom-native Open Measurement guide says to show/register the ad view on the main thread and that `DisplayOpenMeasurement.start()` must run on the main thread. See [Load an ad](https://developers.google.com/ad-manager/mobile-ads-sdk/android/custom-native-omid#load_an_ad) and [Register your view](https://developers.google.com/ad-manager/mobile-ads-sdk/android/custom-native-omid#register_your_view_and_begin_measuring).

## Practical conclusion for this project

`MobileAds.initialize()` may run on an IO/background dispatcher. For the Legacy SDK, keep the public ad request entry point (`AdLoader.loadAd`/`loadAds`, `InterstitialAd.load`, `AdManagerAdView.loadAd`) on the Android main looper. The SDK then performs network/waterfall work asynchronously; putting the call itself on a worker thread is not a supported way to bypass lifecycle or window-focus policy.

The project's `allowWhileVisible`/`canStartNativeRequest` checks are application-level gates, not Google requirements. If they defer a request until `RESUMED`/window focus, moving the same call to a background thread will not make it start—the gate must be changed deliberately (while still dispatching the SDK call to main). A preloaded native ad is independent of the destination view: load it into a cache while the app is eligible to make the request, then bind it to a `NativeAdView` on the main thread after navigation. Do not bind Android views from a worker thread.
