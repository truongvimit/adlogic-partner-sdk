# Everyday tools: standard RetentionKit integration

This example is a real offline catalogue: Notes (create/edit), Saved items (durable copies of notes), Text tools (normalize whitespace and count words/Unicode code points), and Guide (bundled EN/VI content and a calculated reading estimate). Text and saved results stay in this application's storage. A completed operation creates a durable UUID in the app outbox; retrying delivery keeps that UUID. Core dispatch acknowledgement marks it reported. Opening a screen, saving unchanged text, or a failed operation never invents a business success.

## One entry path

`GlobalApp` retains the existing initialization order: tracking → shared ad configuration → Ads/Billing → PayKit → OnboardKit → RetentionSuite → existing welcome-resume observer. `RetentionExample.install` supplies the catalogue, locale, Splash/Main/final Activity facts, known migration aliases and native content. The [suite preset](../retentionkit/SUITE_INTEGRATION.md) owns common configuration, tracking, Billing and Onboard adapters. It is idempotent for the active runtime; a replaced debug runtime receives new owned adapters.

`SplashActivity` extends `RetentionSplashActivity`, preserving its real billing/remote/ad overrides. The SDK base owns capture, materialized saved state and warm/new-Intent Splash policy. Every notification/action, pinned action, widget/shortcut and feedback/rescue entry still executes actual Splash → existing Onboard terminal → actual Main resume → destination. The existing listener retains language selection and delegates once to `RetentionSuite.onOutcome`.

Main has no Retention handoff fields or lifecycle forwarding. The SDK binds Main before onStart and waits for its actual readiness predicate (internet/update/consent dialogs and window focus). Main never permits automatic review/widget prompts. The feature Activity implements `RetentionFeatureHost.onRetentionFeature(entry, destination)` to display business content; capture/new-Intent replacement/recreation, bounded readiness retries and final consumption are SDK-owned. An absent/rejected delivery cannot revive the previous entry, and the ledger is never drained as a backlog. Known retired destinations preserve the original UUID/envelope and resolve only at the final feature boundary.

Normal Main and feature UI expose **Enable notifications** and a read-only **Notification status** action outside the debug section. Permission is explicit and SDK-owned only when that button is pressed; result/return/timeout cleanup and reconciliation require no Activity wiring. Status does not send/refresh notifications. Ordinary default delivery is driven by actual setup, entitlement, permission and host readiness. Existing Onboard permission flows may continue to own their result and call the suite's `permissionChanged` instead.

## Existing Ads integration

Feature screens bind `ExampleEntryNative` to the existing `AdsManager.nativeHelper`, `layout_native_ad_medium`, selected remote style, and a child lifecycle which is destroyed when that slot changes or its host ends. Notification sources select `native_noti`; widget/feature shortcuts select `native_widget`; feedback rescue selects `native_uninstall`; ordinary in-app browsing selects `native_home`. SDK feedback uses the same adapter in its optional native slot with the controller's lifecycle.

The added entry keys in both ad assets inherit the corresponding existing splash/native-home units. The debug asset stays pinned to official AdMob test IDs by existing AdRemoteConfig behavior; no remote override or bypass of consent/Billing/UA is added. Release uses the existing configured units and normal shared RC. A request or a skipped/failed load is not an impression. Debug observations come from the actual helper request call, helper terminal state, loaded callback and impression callback; navigation is independent of native fill.

Settings/feature feedback buttons use `feedback.openViaEntry()`. The standard survey has optional reasons, feature rescue, Keep, native content and Continue to **Android's own uninstall confirmation** for this package, with app management available as an explicit fallback. Device tests cancel the confirmation. Manual Rate uses Play Store; automatic review uses real completed business operations. Neither callback reports rated=true.

## Shared configuration and customization

The suite preset configures `FirebaseRetentionConfigSource` with `RetentionLegacyConfig` and reads the common legacy keys and versioned `retention_config` through the same suite client/fetch. JSON overrides/removals win; absent keys do not erase defaults; invalid updates preserve last-known-good state. The notification module owns the common campaign profile, family channels, calendar restore, rotation and guards. This app supplies generic content/resources, not another scheduler or Firebase mapper.

To adapt this example: replace the four catalogue labels/icons/descriptions, supply the final feature router once at installation, bind your existing medium native presentation, and report a stable business operation UUID only after your real operation succeeds. Optional feedback native/custom views still use the SDK controller and lifecycle. The normal permission button calls `RetentionSuite.requestNotifications`; no automatic prompt is added.

## Upgrade compatibility

The app keeps `retention_example_data_v1` / `state`. Versioned synchronous migrations preserve input, last result and every outbox operation's original feature/result/UUID/reported bit. Retired destinations map to `notes`, `saved_items`, and `guide`; `text_tools` is unchanged. Existing saved content is copied into generic Saved items through `ExampleLegacyData`, which is only a legacy decoder. New visible catalogue/actions/tests have no translation/travel business identity. Already-persisted legacy envelopes keep their original token; only the final resumed host recognizes and consumes the explicit known alias before showing its canonical destination.

No SDK/core files or other app preferences are cleared by migration. A failed preference commit restores memory as well as retaining durable pending work. Removing a Saved item leaves its original note intact.

## Debug QA and evidence boundaries

The debug controls are collapsed under **DEBUG · engine controls**. Activating a fixture replaces only `retention_example_engine_qa_v1`, selects a known free/setup state, test clock, zero grace/guard and isolated arbitration, and disables automatic review unless explicitly enabled. The fixture omits the Billing **Retention adapter** so authoritative production entitlement cannot overwrite the explicitly declared synthetic state; existing Ads Billing/consent policy remains active. It retains the same standard Splash router, Onboard adapter, host gate, terminal listener, Main handoff and real Android/ad transport. The real completed Onboard state overrides an initially pending setup fixture; the harness never clears normal Onboard state or forces an active flow. It does not force an ad to load or mark one shown.

Fixture configuration is process-local. A cold Application restart returns to ordinary configuration and the standard router, with authoritative Billing readiness; it does not silently recreate synthetic state. “Restore production defaults” detaches the fixture and installs a fresh normal bridge. Business data and ordinary SDK state remain separate from the fixture file. Event history is debug-only.

The debug wall clock advances with real elapsed time, so the real three-second ad-return timer reaches its persisted due time. An explicit calendar jump resets that anchor and continues ticking; elapsed-time leases remain unchanged. Calendar injection passes the module's actual persisted envelope to its actual receiver. It advances wall time to `max(current,due)`, never rewinds before setup or refreshes an expired slot; elapsed time remains real for lifecycle bounds. DAILY tests pin tomorrow 08:56 before fixture installation, proving the saved08:00 slot is past-due but inside its09:00 expiry independent of real clock time. These tests prove engine/permission/channel handling, not AlarmManager/Doze wake timing.

The Android suite observes actual `Application.ActivityLifecycleCallbacks`: Splash created/resumed → Main resumed → selected feature/SDK feedback resumed. Creation may observe an OS-owned REUSABLE template before Splash captures it. The observer requires the same actual Splash instance and unchanged source/destination/action/campaign/instance/expiry across materialization; from Splash resume through Main and the destination it requires the complete exact ONCE envelope and durable consumed receipt, then rejects replay. It covers every pinned action and all widget/feature-shortcut destinations, warm/cold routing, rapid explicit entries, actual completed-Onboard synchronization/suppression, usable feedback rescue, cancelled uninstall confirmation and real review transport with honest terminal outcomes. Unfinished-onboarding abandonment remains covered by actual receiver/module tests; this established-installation device suite does not pretend a synthetic flag is an unfinished real first-open UI. Route waits cover the real Splash remote/ad barriers (45s); engine-only waits keep their narrower bounds. No diagnostic boolean substitutes for an Activity lifecycle or consumed receipt. Native request/loaded/impression evidence is recorded separately. During route waits the instrumented harness only acts while the foreground Activity is the real, focused GMA AdActivity in this app. It discovers a currently exposed semantic Close/Đóng control and records its actual attributes before clicking; otherwise it uses a real Back gesture. It rechecks the Activity before input, never guesses a close position or an unlabelled image button, and retains the ad’s required wait. A sent gesture is not proof of ad completion; the real terminal callback and subsequent lifecycle still determine the result. It never calls an ad callback or sends Back to a different Activity to manufacture completion. Debug tag `RetentionNativeEvidence` records the same actual placement/phase observations as the native callback list, separately from screenshots or impressions.

The device owner must grant POST_NOTIFICATIONS, complete the real first-open/consent flow and ensure exclusive device use before the suite. Tests do not automate consent agreement or uninstall the app. Teardown closes Activities it created, cancels only SDK-tagged notifications, deletes only its uniquely owned blocked-channel fixture and restores standard runtime defaults. Do not clear all application data on a user's installation.
