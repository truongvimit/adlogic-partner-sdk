# Retention notifications

A standalone core-only module for common retention notifications. No ads, Firebase, widgets, Play review, WorkManager or Compose dependency. Install in `Application.onCreate`; core owns process lifecycle, durable config and feature routing.

## Installation and common entry chain

```kotlin
val notifications = RetentionNotifications(RetentionNotificationOptions(
    smallIconRes = R.drawable.ic_notification,
    preset = NotificationPreset.COMMON_PLAN,
))
```

`COMMON_PLAN` is the default. `LEGACY_SDK` preserves the original SDK cadence and `rk_retention_<campaign>` channel IDs; it is **not** a Translate preset. Pick the preset when installing. Remote patches override individual policy values, without silently switching channel identity.

Supply localized, app-neutral feature IDs/labels/descriptions and a router targeting the host's real Splash. All body/action entry intents must follow **Splash → existing entry interstitial completed or legitimately skipped → Main actually resumed → destination**. Use the umbrella's standard entry integration with OnboardKit for the common chain; direct-module partners own the equivalent lifecycle handoff. `recordOpened()` only records an accepted entry, and never navigates or consumes it. Dismiss/X/Later is an internal broadcast that cannot open UI. Every action uses a distinct immutable direct Activity PendingIntent; no notification trampoline exists.

The host owns permission prompts, genuine setup completion, authoritative entitlement, consent/ads and real feature functionality. No-IAP hosts may explicitly set `NON_SUBSCRIBER`; `UNKNOWN` and subscribers suppress new marketing. An already-posted matching pending Lockscreen is retained during transient UNKNOWN, with wake paused; an actual subscriber cancels it. In `COMMON_PLAN`, completed setup is eligible immediately (`setup_grace_ms=0`): there is no extra day of waiting for Reminder, Daily or exit campaigns. Active unfinished setup remains protected; the setup-specific abandonment extension keeps its configurable **24 elapsed hours from installation**. The canonical “first day while still setting up” rule does not prescribe 24 hours after completion or define a rolling-versus-calendar-day calculation. Entry taps never bypass unfinished setup.

## Shared profile and source precedence

Primary references: the common `Notification System Implementation & Test Plan` (complete MD plus DOCX image tables), the newer MO lockscreen v1.0 document (2026-08-17), `Noti.pdf`, and `NOTIFICATION_GUIDE.pdf`. Generic templates and priorities follow the main plan; the detailed MO default skip logic takes precedence over its earlier repeat-wake overview. Source-app labels/art are examples. The reopened audit of unchanged original files, their hashes and exact page/line references is `SDKOptimize/retentionkit-default-fix/canonical-audit.md` outside this repository. It supersedes the earlier audit’s recommendation to retain the invented post-setup grace. Older acceptance records remain historical.

| `pinned` / 7106 | Foreground/open; quiet four-feature extension, skip while visible | 6 h | none / unbounded |
| `lockscreen` / 7107 | **11:30, 17:00, 20:00**, background | 1 h to deliver; **no posted timeout** | 1 h / 3 |
| `app_exit` / 7108 | Completed setup, no qualifying ad click, confirmed departure +3 s | 5 min | 15 min / unbounded |

Delivery/display TTL and navigation lifetime are separate. An expired delivery is still rejected before posting, and Android receives the same display timeout. New notification envelopes do not copy that display deadline into `expiresAtMillis`: a user who taps before timeout can complete real language/onboarding/paywall work without losing the accepted route after five minutes. Core still bounds one-shot routes to seven days from the occurrence's creation time; PINNED and persistent lockscreen templates materialize a fresh ONCE route on each delivered tap with the same seven-day bound. This does not guarantee a notification remains visible or bypass setup/feature validation. Already-posted or already-staged envelopes from the prior implementation retain their explicit expiry; this change cannot rewrite them retroactively. Subsequent posts use the corrected envelope.

The main plan's “Kill App” test also covers a no-click departure; its PDF/reference implementation describes ad-click departure. `APP_EXIT` supplies the former as an observable generic campaign. One departure arms one campaign; `AD_RETURN` wins when a valid click exists. There is no OS kill callback. A hard kill before background scheduling is unobservable. Common exits save a one-shot inexact alarm before the in-process timer; process death after saving can recover the same occurrence, with every gate rechecked. Foreground, config changes, subscriber/unknown entitlement, host UI and external transitions cancel pending exits. Timer completion and OS delivery race against the same saved envelope and claim. Onboarding remains session-only; restart does not invent an active setup scope.

Daily sound/HUN conflicts between source attachments; the shared default conservatively follows the quiet guide. Existing channels are never deleted/recreated or upgraded to evade user choices. `channelIds` overrides preserve a migrated app's exact existing channel choices. Existing SDK IDs7101–7107 stay stable; the source1001-series IDs were suggestions, not forced migration IDs.

Arbitration: lockscreen > Updates group > daily > reminder. A due, eligible, uncapped higher-priority scheduled occurrence wins even if a lower-priority receiver arrives first. Existing Updates posts block another Updates post until dismissed/opened. A durable **30-second guard** prevents cross-family bursts; this numeric value is a chosen configurable default because the main document leaves it blank. Lower-priority calendar/exit occurrences can be skipped. The current foreground open retains an eligible quiet surface while readiness is blocked. Initial pinned creation spends the guard; if Reminder posts first, one bounded guard-delay retry lets PINNED follow automatically. An already-visible PINNED surface is skipped without another post. Background or shutdown cancels this foreground retry, including stale callbacks. No burst replay of old opens is created. Per-family cooldowns/caps still apply; neither priorities nor the guard can bypass permission, entitlement, phase or TTL.

The exact local slots, replacement default false, three-second confirmed departure and Reminder15min are supported by the common references. Winback14–45d and max3 are explicit PDF requirements. The two-day new-user selector is a retained reference-implementation extension, not a canonical eligibility gate: both common lockscreen slot lists are identical by default. Delivery TTLs, cooldowns outside Reminder, remaining numeric daily caps, guard30s and token5min bounds are SDK choices. The undocumented post-setup24h wait, Reminder4/day, PINNED2/day and exit2/day limits have been removed from COMMON_PLAN; explicit partner overrides remain supported. `LEGACY_SDK` keeps ≥48h unbounded inactivity, winback12h cooldown/1 per day/no lifetime cap, onboarding grace0, no shared guard/arbitration, one-hour posted lock timeout, in-process ad delay and APP_EXIT disabled. That48h inactivity was the original SDK choice, not Translate's two-day cohort.

Foreground readiness is automatic after the one `ProcessForeground` event: setup, authoritative entitlement, host/external-scope completion and `runtime.reconcile("permission_result")` retry the same pending open. Low-level hosts should reconcile after an actual permission result; the standard suite owns this handoff. Successful submission or an already-visible pinned surface completes that foreground request. Repeated ready callbacks do not create another successful open. A reentrant partner callback gets at most one coalesced recheck; continuously changing readiness cannot spin indefinitely. `refreshForegroundNotifications()` remains an optional explicit hook and returns both `Skipped("background")` outcomes when called in background.

`notifications.status()` is a read-only `NotificationStatus(installed, revision, foreground, campaigns)` snapshot. Each `NotificationCampaignStatus` contains `campaign`, `enabled`, `pendingForeground`, `lastOutcome` and `nextAlarmAtMillis`. `lastOutcome` records the last actual attempt in the current process: `Skipped.reason`, `Failed.stage`, or `PostSubmitted`; null means no attempt. It does not claim the current permission state or a visible notification. `nextAlarmAtMillis` is the requested inexact alarm/checkpoint time. Reading status never posts, reconciles, requests permission or changes persistent state. Before attachment it returns `installed=false` with an empty campaign list.

Use core's cached PATCH API; absent keys preserve existing values, explicit removal restores the selected preset's default. No second Firebase client is initialized. `NotificationLegacyConfig.keys` exposes exact legacy fetch keys and `map(presentValues)` returns `NotificationConfigMigration(overrides, unsupportedKeys)`; `translate()` remains a source-compatible alias. Feed actual fetched **present** values to this mapper, then use the same config owner to apply a single combined patch.

Exact aliases: `notiDailyEnabled→daily.enabled`, `noti_daily_slots→daily.slots`, `notiWinbackEnabled→winback.enabled`, `noti_winback_slots→winback.slots`, `notiLockscreenEnabled→lockscreen.enabled`, **`noti_lockscreen_slots→lockscreen.slots`**, **`noti_lockscreen_slots_new→lockscreen.new_user_slots`**, **`notiLockscreenReplace→lockscreen.replace`**, `notiClickedAdsEnabled→ad_return.enabled`, `notiOnOpenEnabled→reminder.enabled`, `noti_new_user_days→new_user_days`, `noti_lockscreen_wake_seconds→lockscreen.wake_duration_ms` (integer1–20 seconds converted to milliseconds; invalid input rejects the combined revision). No undocumented `notiKillAppEnabled` alias is invented. Premium marketing, arbitrary remote image/content JSON and keys belonging to other modules are reported unsupported here, not silently accepted.

## Content and lockscreen lifecycle

The generic default catalogue combines **different campaign framing** with the real feature label/description; EN/VI strings are bundled. Daily uses BigText. Winback/exit use BigPicture with a bounded local image (a bundled generic illustration is the fallback); exits have independent collapsed “Before you go” and expanded feature titles. Lockscreen includes a compact48dp title/body/CTA/X layout and a separate expanded image layout; heads-up uses the compact version. Pinned exposes four distinct feature tiles in both compact and expanded layouts. Runtime-localized close/open text and accessibility labels are applied explicitly so SystemUI locale cannot replace the app choice. Supply local `NotificationContent` for app copy/art, including `expandedTitle`, or decorate with `NotificationRenderer`. All supplied destinations must be allowlisted features. Default CTA is Action now/Mở ngay. Custom views must use the supplied PendingIntents; the SDK restores main/delete/standard actions and checks all gates again after renderer and storage boundaries.

Common lockscreen selection is random excluding the previous recorded content; rotation survives restart and is not bound to a slot. A single item may repeat. Other families cycle deterministically. Failed/blocked rendering or notify does not advance rotation. Default replacementfalse leaves an untouched OS notification in place across slot/day boundaries. No repeat alert, midnight reset or one-hour posted timeout occurs. Replacementtrue replaces the same family ID at eligible slots and rotates. X/swipe cancels only the matching occurrence; ordinary app foreground also dismisses the old lockscreen. Delivery TTL only controls whether a queued alarm may first post. The persistent lockscreen PendingIntent uses core's reusable-template mechanism so a days-old visible notification still creates a fresh, once-consumed entry when tapped; selected feature validation still applies.

The MO20s/max2 requirement is implemented as bounded requests using public `SCREEN_BRIGHT_WAKE_LOCK | ACQUIRE_CAUSES_WAKEUP`. `COMMON_PLAN` enables this by default; no Activity is started, no full-screen intent is used, and `ON_AFTER_RELEASE` is absent. Each screen lease is timed at at most20s and is released on cancellation. The normal `WAKE_LOCK` permission is declared only by this module; `TURN_SCREEN_ON` is not requested. The legacy compatibility path remains present in AOSP Android14–16 releases even though the wake flag is deprecated. Level/permission checks can reject a request; acquisition alone does not certify physical display-on. [PowerManager](https://developer.android.com/reference/android/os/PowerManager.html), [WakeLock](https://developer.android.com/reference/android/os/PowerManager.WakeLock).

The controller first verifies the exact owned active occurrence and rechecks current configuration, setup, background, entitlement, notification permission, channel/group and wake capability. If Android posting has not settled yet, at most three delayed checks100/300/1000ms share a timed CPU-only partial lease of at most2s; it closes as soon as confirmation ends. Screen-wake attempt claims are persisted before acquisition and never exceed two for a message, including process restart or uncertain failures. Send TTL/caps are not spent again to wake an existing persistent message. Observer/checkpoint callbacks are occurrence-bound; replacing a message prevents old callbacks from spending the new budget.

A later non-interactive transition can request the second wake only while the same notification remains eligible. The first lease has a10s settling margin before re-wake, plus one inexact CPU-wakeup alarm fallback. If that cold checkpoint meets UNKNOWN, at most six readiness checkpoints back off30s/1m/2m/4m/8m/16m; there is no indefinitely running polling timer. If the matching asynchronous post confirmation first meets UNKNOWN before any screen-wake claim, that confirmed first-wake decision is also persisted with a30s inexact fallback and the same bounded readiness checkpoints. Verified-free reconciliation can finish this pending first wake immediately while the display remains off, including after process recreation; a restart without that saved decision does not invent a wake request. Duplicate UNKNOWN callbacks never reset the checkpoint budget. A later authoritative callback may finish the retained pending decision even after checkpoint exhaustion. These are bounded recovery choices, not exact-delivery guarantees. Dismiss/swipe/open, subscriber, disable and shutdown release owned handles and cancel retry work. UNKNOWN pauses wake while preserving only the matching previously-posted Lockscreen, not permission to post new marketing. Boot restore still requires Application installation and available credential storage after unlock; it never opens launcher.

Telemetry separates `wake_requested`, `wake_lock_acquired`, `wake_observed` (interactive observation with unproven attribution), `wake_blocked`/`wake_failed`, `wake_released` and `wake_cancelled`. **20s bounds the SDK lease, not a promise to force physical screen-off** against user screen timeout, USB stay-awake, another app or OEM policy. A user can also turn the display off earlier. `RTC_WAKEUP` only protects alarm execution; no physical wake success is inferred from it. Root device acceptance measures the actual display transition and owned lock separately. The complete source-based feasibility report is `SDKOptimize/retentionkit-default-fix/platform-wake.md` (07/09/2026).

## State, scheduling and migration limits

The owned `notifications.state.v1` namespace atomically reserves occurrence, daily/lifetime capacity and guard before notify. A final pre-notify gate can atomically abort its proven-unposted claim, refunding capacity and reopening only that occurrence for valid UNKNOWN/current-revision recovery. Once notify has been invoked, a thrown call keeps conservative occurrence dedupe even when numeric capacity is refunded; a crash/receipt-storage failure leaves unknown delivery and conservatively spent capacity. Lifetime counts do not disappear with the eight-day occurrence ledger, a new day or process restart. Successful submission advances rotation and global guard. `PostSubmitted(receiptPersisted)` describes a returned notify call, never a visible impression. Config revision, permission, channel/group, entitlement, host transition, setup phase, time bounds, cap, active-group state and rotation are rechecked; a stale alarm cannot revive a removed config.

Calendar identities remain stable per family/local slot; handled dates prevent backward-clock duplication. A cold receiver with restored completed setup and current-process `UNKNOWN` entitlement retains the original due occurrence rather than spending the date. Verification retries it immediately while its original TTL remains valid. If the process dies before verification, durable inexact checkpoints back off by30s,1m,2m,4m,8m,16m (at most six retries), followed by expiry cleanup. Duplicate callbacks do not spend checkpoints. Only the alarm trigger time changes; original due, expiry, occurrence and revision remain fixed. These checkpoints are bounded SDK recovery choices, not canonical timing guarantees. A subscriber, foreground, permission/channel or other final eligibility decision still skips the calendar occurrence; expiry or a removed/replaced config cannot replay it later. Cached free entitlement is never trusted to bypass a current `UNKNOWN`. Reboot/package replacement/clock/timezone reconciliation rearms desired records from cold local configuration. `GregorianCalendar` works on API24: nonexistent DST time shifts forward; repeated time chooses standard-time occurrence. `setWindow(RTC_WAKEUP, due, 10min, ...)` requests an **inexact** window: RTC_WAKEUP is0 and can wake CPU, not screen. Android/Doze/OEM restrictions can defer longer. Force-stop suspends execution until user interaction. No scheduling/display timing SLA is claimed. Alarm fallback after process death is also inexact;3s is only the live timer's intended confirmation delay.

Disable and cancel the old engine's **known owned** alarm identities before migration. Do not delete user-disabled channels. Existing eight-day attempts/cooldowns and7101–7107 identities are retained; new lifetime limits import retained submitted/uncertain attempts once before pruning, without resetting known capacity; already-pruned legacy historical sends cannot be reconstructed. Cross-process storage writers remain unsupported. Active Process progress/FGS and battery-optimization UI from the source plan belong to real host jobs, not these marketing campaigns.
